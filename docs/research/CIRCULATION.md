# 全身大地图血管与心脏设计草案

2026-10-05。目标尺寸为 4096 × 8192 个逻辑格，共 33,554,432 格，面积为当前地图的 32 倍。研究阶段完成主要血管拓扑、坐标布局和路径检查；下文记录当时的设计草案。后续游戏运行地图已切换为 4096 × 8192，实际管壁和通行口实现见 [VESSELS.md](../VESSELS.md)。4096 × 8192 尚未通过原生性能验证，不能视作引擎上限。

建议先做完整循环骨架，再生成器官内的微血管。玩家应能沿血流快速远征，也能进入组织，从旁路迂回和截断补给。下面的坐标、宽度、速度、心跳周期都是游戏设计建议，单位为逻辑格或模拟秒，不代表真实人体比例或医学参数。

## 保留的解剖关系

基本循环为右心房 → 三尖瓣 → 右心室 → 肺动脉瓣 → 肺动脉 → 肺微循环 → 肺静脉 → 左心房 → 二尖瓣 → 左心室 → 主动脉瓣 → 主动脉 → 组织微循环 → 静脉 → 上或下腔静脉 → 右心房。动脉、静脉按流向心脏的关系命名；肺动脉运送低氧血，肺静脉运送高氧血。肠胃与脾的主要回流先经肝门静脉进入肝脏，再由肝静脉进入下腔静脉。依据：[OpenStax 循环通路](https://openstax.org/books/anatomy-and-physiology-2e/pages/20-5-circulatory-pathways)。

心肌有独立的冠脉供血与静脉回流。心腔内的血液和心肌的营养供应在游戏数据中也应分开。依据：[OpenStax 心脏解剖与冠脉循环](https://openstax.org/books/anatomy-and-physiology-2e/pages/19-1-heart-anatomy)。

本图采用人体正面投影，因此屏幕左侧对应人体右侧，肝脏放在屏幕左侧、心脏偏向屏幕右侧。深浅层器官展开到同一平面；真实的三维位置和比例只保留识别关系。图上的线交叉不自动形成通路，只有共同的节点编号才代表相通。被压到同一平面的深层血管，可通过有名称的连通口表达，不需要改回 2.5D。

## 全身布局与血管骨架

当前原型有 95 个节点、120 条有向连接、17 个聚合微循环床。微循环床是一个器官或区域的总入口和总出口，后续可以展开成许多真实可玩的分支，不能把这 120 条连接当成所有血管的最终数量。

| 区域 | 建议布局 | 主要通路与战略用途 |
| --- | --- | --- |
| 头脑 | 中心约 2048,690 | 颈内与椎动脉供血，脑底动脉环连接，颈静脉回流；适合多入口与外围迂回 |
| 胸部与肺 | 两肺中心约 1400,2630 和 2960,2630 | 右心室分别送往两肺，肺静脉返回左房；肺泡出口作为氧气与补给目标 |
| 心脏 | 外框左上 1740,2180，宽 1010、高 1270 | 四心腔与四瓣膜，左右循环独立连接；心肌外围另有冠脉通路 |
| 腹部 | 肝约 1510,3630，肠约 2060,4510 | 腹腔干与肠系膜支路，门静脉将肠道营养送肝；腹部形成补给争夺区 |
| 双肾 | 1390,4210 和 2960,4210 | 独立肾动脉、肾静脉；建议用于代谢过滤与污染处理 |
| 双上肢 | 由肩向地图两侧下垂 | 锁骨下 → 腋 → 肱 → 桡与尺 → 掌弓；双前臂分支提供绕行路线 |
| 盆腔与双下肢 | 约 y=5000 后分叉，足端至 y=8000 | 髂 → 股 → 腘 → 胫前与胫后 → 足弓；长距离远征，股骨骨髓设生产目标 |

第一批制作重点是主动脉与腔静脉、心肺、肝门静脉、四肢双分支、脑循环和冠脉。浅静脉、胸壁细支、完整脊髓供血、每个手指与足趾的微循环，以及淋巴回流可在第二批加入。人体外形保留手足轮廓；当前骨架并不代表已完成全身解剖。

## 心脏成为一片可玩的区域

建议心脏内保留四个相通关系明确的腔室，心肌壁为独立组织，心包外围为可集结区域。血流乘载经过心腔，普通组织行军只走心肌外围和冠脉周边。禁止细胞直接穿过心脏隔壁，以免左右循环被地图捷径混在一起。

四个瓣膜各有入口、出口、方向、节律相位和通行容量。建议第一轮用 1.2 模拟秒的视觉周期，表现充盈、收缩与血流推进；队伍在入口排队，在允许的阶段通过。瓣膜应提供清晰预告，暂时闭合让细胞等待，不能在关门时无提示地夹死部队。冠脉供血与心肌状况影响搏动效率，心脏局部受损先降低全身运输与供给，再形成危机任务。

心脏不是某个阵营的普通基地。建议它属于全身公共系统，争夺重点放在冠脉入口、瓣膜周边、修复点和外侧据点。这样不会因为先占一个点就立刻获得整个人体，也能留下外围迂回空间。

## 血流如何服务调兵

将组织移动和血流运输分成两种导航模式。组织与血管壁附近允许双向行军；主血流按循环方向运输。在器官的指定出入点切换模式，不能从任意血管位置穿墙下船。普通壁边路线、组织绕路与血流路线一起参与路线选择，玩家可选择最快、最安全或避开敌方控制点。

| 层级 | 建议完整通行宽度 | 首轮玩法 |
| --- | --- | --- |
| 主动脉、腔静脉 | 32 到 48 格，极大段最多 64 格 | 长途运输主干，中央快速流、两侧低速带 |
| 器官与肢体动静脉 | 12 到 24 格 | 分支战场、装卸点、阻塞与旁路 |
| 小动静脉 | 4 到 10 格 | 局部包抄，队伍队形逐渐收窄 |
| 毛细血管 | 2 到 6 格 | 工细胞与游走细胞通道；大细胞改走宽支路 |

初步建议主干顺流乘载速度为每秒 20 到 32 格，壁边流速低于每秒 0.5 格；具体值需要手感测试。中央高速流不承担逆流行军，逆流走壁边或组织。堵塞同时影响可用宽度、运输容量和器官供给，所有变化都通过同一血管数据驱动。血管中不得自由摆放普通建筑；营地与设施放在组织侧的出入点。

用草案折线路径、恒定顺流速度 28 格每秒估算，左心室至脑入口约 1.7 分钟，至右手约 3.0 分钟，至右足约 4.6 分钟。这些值不含瓣膜等待、拥堵、装卸和血流脉动，是平衡候选值，不是实测。按当前工细胞 2.4 格每秒走同一右足路径则约 54 分钟，说明大地图必须有快速运输与远方集结点，不能只扩大地图让玩家等待。

## 4096 乘 8192 的实现条件

研究前的代码使用单一 `D.MAP`，并把它同时当作宽度、高度、索引步长和存档校验尺寸。必须先改为 `mapWidth`、`mapHeight` 与明确的行步长；不是把 `MAP=1024` 改成一个更大的数即可。

| 现有模块 | 需要改变的职责 |
| --- | --- |
| Data 与 Util | 拆分宽高；格子键为 `(y-1)*width+x`，坐标还原使用 width |
| World 与 Anatomy | 重做全身比例与器官轮廓；区块横纵数量分开，索引描述按需建立 |
| Path | 血管图用于跨器官规划，区域门户用于组织远行，局部 A* 只处理当前路径段；禁止失败后全图细格搜索 |
| Bloodstream | 红细胞沿真实边的弧长运动、从指定汇流点换边；绘制不推进供给，不消耗模拟随机数 |
| Render、View、Input 与 HUD | 适配长条地图与边界；全身总览、器官视图、局部战场使用不同细节级别 |
| Save 与 AI | 新存档保存宽、高、生成器版本、血管状态和乘载状态；AI 通过血管与区域图规划远征 |

32 格区块下全图为 128 列、256 行，共 32,768 块。开局只生成附近资源和区块数据，不能创建三千多万个 Lua 格子表项。建议使用可淘汰的地形缓存、持久化资源变化以及分块迷雾；缓存与区块描述不要随着探索无上限保留。当前 `s.tiles` 的惰性缓存会保留读过的格子，`W.indexChunks` 会预建全部描述，这两处在大图上需要处理。

每 16 格一个总览采样时，是 256 × 512 共 131,072 个采样点。总览应分帧生成并缓存，不能每帧遍历全图；单位与资源仅在可见区域绘制。高倍镜头显示可爱细胞与微状态，器官视图显示战术分支，全身视图显示器官、主干、据点与部队群标记。不能生成一张覆盖全部世界像素的巨大纹理。

血管数据采用节点和有方向的边，边保存控制点、弧长表、宽度、供血属性、通行限制与状态。分叉通过共享节点连接；空间查询使用区块到血管段的索引。固定主干和器官口保证整图连接；种子只改变器官内细支、局部组织和事件。跨区微血管接口由种子、器官编号、区块边界共同确定，防止区块接缝断裂。首轮供给采用图上的容量与来源传播，不引入真实流体或医学压力模拟。

存档建议升级到 v4。旧 v3 世界按旧生成器与旧尺寸恢复，不放大旧坐标，也不把旧迷雾键直接解释成新图的格子。新尺寸通过新开局进入；缓存与粒子不入档，血管阻塞、修复进度、供给和部队乘载位置必须入档。

## 原型验证与下一阶段

机器可读布局见 [血管图数据](circulation-4096x8192.json)，检查见 [原型检查结果](circulation-checks.json)。41 项检查通过：坐标边界、整个循环图连通、器官供血与回流、肺循环必须经过肺微循环、门静脉回流必须经过肝、桡动脉断路后尺动脉仍可达手掌、主要股动脉断路导致该足部失去供血，以及矩形格子键的边界往返。它们只验证研究图，不是游戏、栅格碰撞或性能验收。

建议实现顺序为：矩形世界与兼容存档 → 固定全身器官及主血管 → 可玩的心肺循环 → 部队乘载与出入点 → 肝门静脉和主要器官供给 → 程序化微血管与阻塞事件。

仍需验证真实局部地形与血管宽度的一致性、不同单位尺寸的通行、交叉处不会误连、心腔不可穿墙、暂停与变速、移动中存档恢复、AI 和运输拥堵，以及原生桌面和手机的开局耗时、长距离命令延迟、帧时间、峰值内存及探索后的缓存增长。上述验证完成后，才能判断 4096 × 8192 的运行效果。
